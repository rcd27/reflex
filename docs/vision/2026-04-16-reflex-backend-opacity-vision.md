# Reflex: непрозрачность backend как архитектурный принцип

Третий vision ввёл разделение на frontend-категорию спецификации и
backend-категорию реализации, связанные функтором. В разделе 7.1 того
документа был оставлен открытым вопрос о том, как frontend-категория
должна выражать различия backend-семантик (наблюдательная,
queue-and-decide, inline-фильтрующая, driver-level). Были
перечислены три возможных подхода: единая frontend-категория с
богатым функтором, несколько frontend-подкатегорий, типовой параметр
семантики.

Настоящий документ закрывает этот вопрос единственным решением и
возводит его в архитектурный принцип: **backend непрозрачен для
frontend**. Всё, что касается платформенной реальности — механизмы
перехвата, семантика взаимодействия с пакетом, возможности и
ограничения системных API — остаётся внутри backend-модуля и не
имеет никакого типового или синтаксического представления в
frontend-категории.

## Центральный тезис документа

Backend-специфика не выражается в типах frontend-категории.
Frontend-категория проектируется как максимально общая доменная
категория сетевой реактивности; backend-функтор декларирует своё
покрытие frontend-морфизмов и отвергает цепочки, выходящие за его
возможности, **на этапе компиляции приложения**, не на этапе
проектирования цепочки пользователем и не в runtime.

Утечка backend в frontend — архитектурный дефект. Если тип
frontend-морфизма несёт информацию о том, как морфизм будет
реализован, значит абстракция спроектирована плохо: пользователю
фреймворка навязано знание, которое не имеет отношения к его задаче.
Reflex отвергает этот дефект как структурный.

Полная проверка совместимости цепочки с конкретным backend'ом
выполняется системой типов Rust в момент сборки приложения.
Некомпилируемая цепочка — единственно допустимое поведение при
несовместимости; ни runtime-диагностики, ни «мягкой деградации», ни
динамической выборки реализаций не предусмотрено. Это сознательное
проектное ограничение: вся мощь компилятора направлена на то, чтобы
несовместимые комбинации были невыразимы в собираемом бинарном виде.

## 1. Позиция: backend непрозрачен

### 1.1. Принцип непрозрачности

**Backend непрозрачен для frontend.** Это формулируется в нескольких
дополняющих друг друга утверждениях:

- Ни один тип frontend-категории не параметризован типом,
  обозначающим backend или его семантику. Нет `PacketStream<Observation>`
  и `PacketStream<Intercept>`; есть `PacketStream`.
- Ни одна frontend-подкатегория не соответствует backend-семантике.
  Нет `ObservationCategory` и `InterceptCategory`; есть единая
  категория сетевой реактивности.
- Ни один frontend-оператор не требует от пользователя знать, какая
  платформа под ним работает. `detect`, `classify`, `react`, `inject`,
  `tap` — операторы доменной категории, не операторы конкретного
  backend.
- Ни одна ошибка, связанная с несовместимостью цепочки с backend,
  не проявляется в runtime. Если цепочка несовместима — она не
  компилируется.

### 1.2. Почему утечка — дефект

Пользователь фреймворка пишет цепочку на frontend потому, что его
задача — описать *сетевое поведение*, а не *системную реализацию*.
Он выбирает между «детектировать RST-инъекцию» и «детектировать
подделанный ClientHello», не между «работать с NFQUEUE-вердиктами»
и «работать с AF_PACKET-копиями». Это два разных разреза системы, и
смешение их в одном API означает навязывание пользователю
нерелевантного контекста.

Если тип `PacketStream<Observation>` появляется в пользовательском
коде, пользователь вынужден знать, что у него под капотом
наблюдательный backend. Следствия:

- **Нерелевантная когнитивная нагрузка.** Пользователь удерживает в
  голове различие, не связанное с его задачей.
- **Непереносимость цепочек.** Код, написанный в терминах одной
  семантики, не работает в терминах другой — даже когда домен задачи
  это позволяет.
- **Блокировка эволюции фреймворка.** Изменение backend-стратегии
  разработчиками фреймворка требует массовой переработки клиентского
  кода.
- **Загрязнение доменного словаря системным.** Обсуждая сетевую
  задачу, пользователь вынужден использовать слова из другой
  предметной области.

Принцип непрозрачности запрещает эти последствия конструктивно: их
источник — неправильная граница абстракции — устраняется на уровне
типовой системы фреймворка.

### 1.3. Формулировка «какая пользователю разница»

Инженерная формулировка принципа: *пользователю фреймворка безразлично,
как именно пакет попал в его поток — через AF_PACKET, NFQUEUE,
WinDivert или pcap-файл*. Это безразличие — не пренебрежение
деталями, а правильное проведение границы ответственности. Детали
значимы — но значимы для автора backend-модуля, не для автора
прикладной цепочки.

Симметрично: *пользователю фреймворка безразлично, каким системным
механизмом инъектированный пакет попадёт в сеть — через
`PACKET_TX_RING`, через NFQUEUE-вердикт `NF_REPEAT` с модификацией,
через WinDivert-send*. Оператор `inject` означает «отправить пакет в
сеть»; способ реализации этого намерения — дело backend-функтора.

## 2. Механика проверки на этапе сборки

### 2.1. Требование строгости

Ошибки совместимости цепочки с backend — **строго времени сборки**.
Это не уточнение, а ограничение жанра фреймворка. Runtime-проверки
совместимости в reflex не допускаются как проектное решение:

- Динамическая ошибка «ваша цепочка не работает на этом backend» —
  то же самое, что утечка backend в frontend, только отложенная во
  времени. Пользователь узнаёт о проблеме, когда приложение уже
  запущено; это хуже, а не лучше, чем явный тип в сигнатуре.
- Цель фреймворка — гарантировать, что *собранное приложение
  работает*. Если приложение собралось — любая его цепочка
  совместима с backend, с которым оно собрано. Это даёт сильную
  инженерную гарантию, снимаемую с пользователя.
- Система типов Rust достаточна для выражения этой гарантии без
  костылей: ни макросов, ни build-скриптов, ни внешних инструментов
  верификации. Мощь компилятора используется по назначению.

Если цепочка некомпилируема — это диагностика компилятора, адресно
указывающая на несовместимый оператор и на причину несовместимости.
Никакой иной формы ошибки совместимости в reflex не существует.

### 2.2. Capabilities как типо-уровневый контракт

Механизм проверки, совместимый с требованием строгости — **система
capabilities**, выраженная маркерными трейтами:

- Frontend-категория декларирует набор возможностей, которые могут
  требоваться для реализации того или иного морфизма. Возможность
  — например, «способность модифицировать пакет до его попадания в
  сеть», «способность удерживать пакет до вынесения вердикта»,
  «способность наблюдать пакет без воздействия на его поток».
- Каждый frontend-оператор, сигнатура которого нетривиальна с точки
  зрения backend, декларирует требуемый набор capabilities через
  трейт-баунды.
- Каждый backend-функтор декларирует набор capabilities, которые он
  предоставляет, через реализацию соответствующих маркерных трейтов.
- Попытка применить оператор, требующий capability, которую backend
  не предоставляет, проваливается на уровне trait resolution в
  компиляторе.

Такая конструкция обладает ключевыми свойствами, необходимыми для
выполнения требований принципа:

- Пользователь frontend не видит capabilities явно — они встроены в
  трейт-баунды операторов, которые Rust проверяет неявно при
  композиции.
- Backend объявляет capabilities однократно, в своём определении, не
  в месте применения.
- Ошибка несовместимости — диагностика компилятора, указывающая на
  отсутствующую реализацию трейта у конкретного backend'а.

Точный синтаксис, перечень капabilitites, схема именования и связи
между ними — предмет спецификации следующего уровня. Настоящий vision
фиксирует лишь то, что именно этот класс механизмов является
принятым направлением.

### 2.3. Отсутствие runtime-валидации

В reflex не существует runtime-механизма проверки совместимости
цепочки с backend. Это включает:

- отсутствие «registry» backend'ов с проверкой доступности операторов;
- отсутствие dynamic dispatch, позволяющего подменять backend после
  сборки;
- отсутствие feature-flag-систем, отключающих операторы по условию;
- отсутствие fallback-режимов, автоматически подменяющих недоступные
  операторы эквивалентами.

Все эти механизмы по-своему полезны в других жанрах систем, но
несовместимы с принципом непрозрачности: каждый из них открывает
канал утечки backend в runtime поведения приложения, который
пользователь фреймворка вынужден учитывать.

Границей ответственности фреймворка является момент успешной сборки
приложения. После сборки приложение работает как детерминированное
целое; вопрос совместимости цепочки с backend в этот момент уже
решён компилятором и не пересматривается.

## 3. Следствие: frontend — максимально общий

### 3.1. Frontend не ограничен самым слабым backend'ом

Последовательное применение принципа непрозрачности ведёт к важному
решению: **frontend-категория не обязана быть подмножеством
возможностей самого слабого backend'а**.

Альтернативный подход — включать во frontend только те операторы,
которые выразимы на всех предполагаемых backend'ах — был бы
«безопасным», но привёл бы к бедной доменной категории, ограниченной
возможностями AF_PACKET (строго наблюдательный backend). Операторы,
естественные для NFQUEUE (удержание пакета, вердикт) или WinDivert
(inline-модификация), не нашли бы места в frontend, и фреймворк
потерял бы выразительность.

Reflex идёт обратным путём: **frontend — это полный словарь домена
сетевой реактивности**. Он включает все операторы, имеющие смысл в
категории «реактивная обработка сетевых потоков», независимо от того,
реализуется ли каждый оператор на каждом backend.

### 3.2. Backend реализует то, что может

Совместимость обеспечивается не сужением frontend, а полным
описанием каждого backend'а в терминах его capabilities. Backend
декларирует:

- какие capabilities он предоставляет;
- следовательно, какие операторы frontend могут быть применены в
  цепочках, компилируемых с этим backend.

Цепочки, использующие только capabilities, общие для всех
предполагаемых backend'ов — **переносимы**: они компилируются с
любым backend без изменений кода.

Цепочки, использующие capabilities, специфичные для части
backend'ов — **условно переносимы**: они компилируются только с
backend, предоставляющими нужные capabilities; с остальными —
получают ошибку компиляции.

Переносимость, таким образом, становится **свойством цепочки**, не
свойством фреймворка. Фреймворк предоставляет язык, на котором
свойства переносимости выражаются точно и проверяются компилятором.

### 3.3. Семантика морфизмов — фронт, реализация — бэк

Центральный инженерный критерий для размещения понятия во frontend
или в backend формулируется так:

- **Смысл оператора в доменных терминах** — фронт. Что означает
  «детектировать», «классифицировать», «реагировать», «инъектировать»
  — определяется frontend-категорией, независимо от платформы.
- **Механизм реализации оператора** — бэк. Как именно «детектировать»
  устроен поверх AF_PACKET, NFQUEUE или pcap-файла — определяется
  backend-модулем.

Промежуточная зона — то, что связывает семантику и механизм —
**capabilities**. Они существуют и во frontend (как требования
операторов к backend) и в backend (как декларация предоставляемых
возможностей), но не как описание конкретной реализации.

### 3.4. Асимметрия backend'ов — не проблема, а ресурс

Различие семантик backend'ов (раздел 3.4 третьего vision) —
наблюдательная, queue-and-decide, inline-фильтрующая, driver-level —
в настоящей формулировке перестаёт быть архитектурной проблемой и
становится **ресурсом для пользователя фреймворка**.

Пользователь не выбирает семантику; он выбирает, какие операторы
ему нужны. Выбор конкретного backend'а вытекает из этого
автоматически: если операторы требуют capabilities, которые есть
только у NFQUEUE — приложение собирается с NFQUEUE-backend; если
достаточно чисто наблюдательных возможностей — приложение может
собираться с AF_PACKET-backend.

Выбор backend'а становится решением уровня сборки приложения,
аналогичным выбору целевой архитектуры при компиляции: его делает
автор приложения, один раз, на основе доступной ему платформенной
реальности и требований задачи.

## 4. Связь с категорной структурой

### 4.1. Функтор как типовой конструктор

Третий vision определил функтор F: Frontend → Backend как отображение
абстрактных объектов и морфизмов frontend-категории в конкретные
системные ресурсы backend. Настоящий vision уточняет эту картину:

Функтор в reflex — **типо-уровневый артефакт**, не runtime-объект.
Он существует в системе типов как совокупность:

- реализаций frontend-трейтов конкретными backend-типами;
- деклараций capabilities через маркерные трейты;
- связывающих трейт-баундов, обеспечивающих совместимость на уровне
  trait resolution.

Функтор не «вызывается» и не «применяется» во время исполнения. Он
*реализуется* в момент сборки, порождая специализированный
монолитный код, эквивалентный прямой реализации цепочки на выбранной
платформе. Это zero-cost abstraction в точном смысле: граница
функтора не оставляет следа в runtime.

### 4.2. Категорная корректность под непрозрачностью

Законы категории (раздел 6 третьего vision) — ассоциативность
композиции, существование тождественных морфизмов, терминальность
инъекторов, законы Rx-операторов — сохраняются в полном объёме в
frontend-категории независимо от выбора backend.

Это прямое следствие непрозрачности: frontend-категория
*самодостаточна*. Её законы формулируются в её собственных терминах,
без отсылок к backend. Backend-функтор обязан сохранять эти законы в
своей реализации — но это обязательство автора backend, не условие
пользования frontend.

### 4.3. Что меняется в категорной картине

Принцип непрозрачности уточняет формулировку третьего vision в
следующем:

- **Frontend-категория единственна**, не является объединением
  подкатегорий по семантикам. Это следствие отвержения подхода (2)
  из раздела 7.1 третьего vision.
- **Объекты frontend-категории не параметризованы семантикой.** Это
  следствие отвержения подхода (3) из того же раздела.
- **Функтор несёт capability-контракт**, не только отображение
  объектов и морфизмов. Это уточнение подхода (1), превращающее
  «богатый функтор» в «функтор с декларируемым покрытием, проверяемым
  компилятором».

## 5. Границы применимости принципа

### 5.1. Что остаётся backend-специфичным по существу

Принцип непрозрачности не утверждает, что всякое различие платформ
стирается frontend-категорией. Некоторые различия **по существу не
стираются** и должны быть приняты:

- **Производительность.** Одна и та же цепочка на разных backend
  имеет разные характеристики задержки, пропускной способности,
  использования ресурсов. Это не предмет frontend-категории, и
  фреймворк не обязуется их уравнивать.
- **Сопутствующая конфигурация платформы.** Развёртывание приложения
  на NFQUEUE требует настройки iptables/nftables; на AF_PACKET —
  capabilities/permissions. Это — ответственность оператора
  развёртывания, не frontend-категории.
- **Взаимодействие с остальной системой.** Backend встраивается в
  сетевой стек ОС по-разному, и побочные эффекты этого встраивания
  (наблюдаемость другими процессами, взаимодействие с firewall'ом)
  различны. Frontend их не скрывает.

Принцип непрозрачности относится к **структуре цепочки**, не к
**эксплуатационным характеристикам исполнения**.

### 5.2. Что именно гарантирует компилятор

Компилятор гарантирует следующее и ничего более:

- Если цепочка, написанная в терминах frontend-операторов,
  скомпилировалась с конкретным backend — все морфизмы этой цепочки
  реализуемы этим backend.
- Если требуемая capability отсутствует у backend — компилятор даёт
  диагностику, указывающую на конкретный оператор и отсутствующую
  capability.

Компилятор не гарантирует:

- что успешно скомпилированная цепочка будет работать корректно с
  точки зрения сетевой задачи (корректность детектора, правильность
  классификации — ответственность пользователя);
- что runtime-поведение цепочки на разных backend будет идентично
  (что реакция на подделанный пакет произойдёт в одинаковой задержке
  под AF_PACKET и под NFQUEUE);
- что ресурсы платформы достаточны для исполнения цепочки
  (производительность — эксплуатационный вопрос).

Эти ограничения — не дефекты принципа непрозрачности, а его
корректная формулировка. Смешение структурных гарантий и
эксплуатационных — источник распространённых ошибок проектирования;
reflex избегает их явным разделением.

## 6. Отвергнутые альтернативы

Настоящий раздел фиксирует для истории проекта, какие альтернативы
принципу непрозрачности были рассмотрены и почему отвергнуты.

### 6.1. Типовой параметр семантики

Конструкция, при которой объекты frontend параметризованы типом,
обозначающим backend-семантику: `PacketStream<Observation>`,
`PacketStream<Intercept>`. Композиция морфизмов разных семантик не
проходит проверку типов.

Отвергнуто потому, что прямо противоречит принципу непрозрачности:
backend-семантика утекает в тип frontend-объекта, и пользователь
вынужден знать, в каком «мире» он пишет цепочку. Все недостатки
утечки (раздел 1.2) при этом подходе присутствуют в полном объёме.

### 6.2. Несколько frontend-подкатегорий

Конструкция, при которой frontend разбит на несколько категорий,
каждая — для своей backend-семантики: `ObservationCategory`,
`InterceptCategory`. Пользователь выбирает подкатегорию при
построении цепочки.

Отвергнуто потому, что различие между подкатегориями проводится по
backend-признаку, не по доменному. Это та же утечка, замаскированная
под архитектурное разделение: пользователь по-прежнему вынужден
начинать рассуждение с выбора backend-семантики. Принцип
непрозрачности требует, чтобы такой выбор не возникал в
пользовательском коде.

### 6.3. Runtime-выбор backend

Конструкция, при которой цепочка собирается в универсальном виде, а
конкретный backend выбирается в runtime из реестра доступных и
совместимых.

Отвергнуто потому, что несовместимо с требованием строгости
(раздел 2.1): ошибка совместимости в этом подходе неизбежно
runtime, не build-time. Пользователь теряет гарантию «собранное
приложение работает». Дополнительно: runtime-dispatch уничтожает
zero-cost abstractions и вносит в hot-path пакетной обработки
косвенные вызовы, которые ничем не окупаются.

### 6.4. Мягкая деградация

Конструкция, при которой операторы, не поддержанные backend,
автоматически заменяются эквивалентами меньшей мощности — например,
оператор модификации на AF_PACKET подменяется связкой drop+inject.

Отвергнуто потому, что принимает решения за пользователя, не
отражая их в его коде. Если замена drop+inject приемлема для
конкретного случая — пользователь должен выразить это явно в своей
цепочке, а не получить молча. Если неприемлема — мягкая деградация
порождает разницу поведения между платформами, не видимую в коде.
Оба случая — нарушение локальности рассуждений о поведении
программы.

## 7. Открытые вопросы

Принятие принципа непрозрачности не отвечает на все вопросы дизайна
фреймворка; оно определяет, в какой форме допустимы ответы.
Следующие вопросы остаются открытыми и являются предметом
спецификации следующего уровня.

### 7.1. Перечень и структура capabilities

Конкретный список capabilities, их гранулярность, иерархия (одни
capabilities могут быть следствиями других), именование — вопрос
спецификации API. Настоящий vision фиксирует лишь то, что такой
перечень существует как типо-уровневый артефакт.

Предварительные кандидаты, вытекающие из анализа backend'ов:

- наблюдение (observation);
- инъекция нового пакета (injection);
- удержание пакета (holding);
- вердикт над удерживаемым пакетом (verdict);
- модификация пакета in-place (modification);
- фильтрация (filtering) — отбрасывание пакета.

Точный состав, связи и иерархия — предмет отдельной работы.

### 7.2. Диагностика компилятора

Ошибка несовместимости, даваемая компилятором, должна быть
читаемой для пользователя, не знакомого с внутренним устройством
трейтов фреймворка. Стандартные диагностические сообщения Rust при
неуспешной trait resolution редко обладают этим качеством.

Техники улучшения диагностики — трейт `#[on_unimplemented]`, sealed
traits, промежуточные маркер-трейты с информативными именами,
специализированные compile-time проверки — предмет отдельной
спецификации. Целевое свойство: пользователь, столкнувшийся с
ошибкой совместимости, должен прочитать сообщение компилятора и
понять, какой оператор и какая capability не совместимы с его
backend.

### 7.3. Эволюция capabilities во времени

Новые backend могут вводить новые capabilities; существующие
операторы могут получать новые требования. Политика совместимости
(semver, стабильность, депрекация) для capability-системы —
отдельный вопрос, значимый по мере созревания фреймворка.

### 7.4. Взаимодействие capabilities с транспортом

Если приложение reflex разделено на несколько процессов (например,
привилегированный backend-процесс и непривилегированный логический,
как упомянуто в разделе 9 третьего vision), возникает вопрос о том,
как capability-контракт проходит границу процесса: сериализуется ли
он, проверяется ли при установлении соединения, существует ли
«межпроцессный backend-функтор». Это не решается настоящим vision.

### 7.5. Тестовый backend и capabilities

Симуляционный backend поверх pcap-файлов, упомянутый в третьем
vision как необходимый для воспроизводимого тестирования, должен
декларировать свои capabilities. Вопрос: декларирует ли он
**все** capabilities (чтобы цепочки, написанные под любой
продуктовый backend, могли тестироваться на нём), или только
наблюдательные. Первая интерпретация требует, чтобы симулятор
корректно имитировал все семантики; вторая — ограничивает полезность
симулятора.

## 8. Что этот документ фиксирует

Настоящий vision фиксирует следующие проектные решения:

- Backend-специфика не выражается в типах frontend-категории.
- Frontend-категория — максимально общая доменная категория сетевой
  реактивности, не ограниченная возможностями самого слабого
  backend.
- Совместимость цепочки с конкретным backend проверяется строго на
  этапе сборки приложения, через систему capabilities, выраженную
  маркерными трейтами.
- Runtime-механизмы проверки совместимости отсутствуют как класс.
- Отвергнуты три альтернативы: типовой параметр семантики, несколько
  frontend-подкатегорий, runtime-выбор backend, мягкая деградация.

И не фиксирует:

- конкретный перечень capabilities;
- синтаксис объявления capability-требований и реализаций;
- форму сообщений компилятора при ошибке совместимости;
- политику эволюции capability-системы;
- поведение capabilities при пересечении границы процесса.

Каждый из этих вопросов — предмет спецификации следующего уровня,
которая будет формулироваться в терминах, совместимых с принципом
непрозрачности, заданным настоящим документом.

## 9. Резюме

Backend непрозрачен для frontend. Frontend-категория проектируется
как полный словарь домена сетевой реактивности, независимый от
платформенной реальности. Backend реализует то, что может,
декларируя своё покрытие frontend-операторов через систему
capabilities, выраженную маркерными трейтами. Совместимость
конкретной цепочки с конкретным backend проверяется компилятором
Rust в момент сборки приложения; runtime-диагностики
совместимости не существует. Переносимость цепочки между backend
— свойство цепочки, определяемое capabilities, которые она
использует, и проверяемое автоматически. Пользователь фреймворка
пишет в терминах домена; автор backend пишет в терминах платформы;
связь между ними — типо-уровневый контракт, несущий всю полноту
инженерных гарантий фреймворка.
